# module-lang v1.0.1: faster import chains

**Patch.** v1.0.1 makes resolution through a long chain of re-exports cost
near-linear time instead of quadratic. The public API is unchanged, and every
1.0 guarantee still holds.

## Fixed

### Long import chains were quadratic to resolve

`resolve` follows a chain of imports to the module that defines the name, and
checks each hop for a cycle. The modules seen so far were kept in a list and
scanned on every hop, so one resolve through a chain of `L` re-exports cost
`O(L^2)`, and resolving every module in such a chain cost `O(L^3)`. A project
with a long re-export chain, opened in an editor that resolves each module's
imports, paid for that on every pass.

The name is the same at every hop, so a cycle exists exactly when a module
repeats. The resolver now keeps the visited modules in a set, and one resolve
costs `O(L log L)`. In a debug build, a chain of 32,000 modules went from about
3 s to a few milliseconds.

Cycles are reported exactly as before: the error names the first module the
walk returns to.

## Tests

`tests/chain_cost.rs` compares resolve times for chains of 4,000 and 32,000
modules and fails if the longer one costs more than 30 times as much (quadratic
work costs about 64 times as much). It also checks that a cycle is still
reported at the repeated module.

## Upgrading

```toml
[dependencies]
module-lang = "1.0"
```

No code changes are needed.
